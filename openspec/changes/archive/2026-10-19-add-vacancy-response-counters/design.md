# Design

## Context

Проект пустой: в репозитории только `openspec/`. Мотивация описана в proposal.md (раздел Why), требования — в `specs/vacancy-response-counters/spec.md`.

Что наблюдалось на hh.ru 2026-10-19 (анонимно; Firefox 158 и Chromium):

- **Начальное состояние страницы** лежит в `<template id="HH-Lux-InitialState">`: JSON, экранированный как HTML. После гидрации элемент остаётся в DOM.
- **Поиск:** `vacancySearchResult.vacancies[]` с полями `vacancyId` (number), `responsesCount`, `totalResponsesCount`. Поля были у 50 из 50 вакансий выдачи.
- **Вакансия:** `vacancyView.vacancyFull.extraVacancyFields` с полями `vacancyResponsesCount` и `totalResponsesCount`. Идентификатор вакансии берётся из URL `/vacancy/<id>`.
- **Карточки поиска:** `[data-qa="vacancy-serp__vacancy"]`, заголовок — `a[data-qa="serp-item__title"]` с `href` вида `/vacancy/<id>?...` и `target="_blank"`. CSS-классы хешированы.
- **Пагинация — SPA:** документ не перезагружается. XHR идёт на тот же URL `/search/vacancy?...` с `Accept: application/json`, `x-is-spa: true` и антибот-заголовками. Ответ — полное состояние страницы в JSON, с теми же полями. `<template>` при этом не обновляется и устаревает.
- **Повтор запроса без заголовков сайта** вернул XML вместо JSON, поэтому повторять запросы сайта нельзя, можно только наблюдать их.
- **Сравнение полей на 9 вакансиях:** одноимённые поля на поиске и на странице вакансии не совпадают по значению. Смысл установлен лишь частично, поэтому поля выводятся под исходными именами.

## Goals / Non-Goals

**Goals:**
- Ноль дополнительных сетевых запросов, ноль секретов, ноль сохранённого состояния.
- Обработка данных не должна задерживать и ломать страницу.
- Разбор формата данных изолирован в чистых функциях, которые проверяются тестами на зафиксированных образцах.

**Non-Goals:**
- Поддержка Chrome и других браузеров. Используется Firefox-only API `filterResponseData`.
- Региональные домены (`hh.kz`, `rabota.by` и т. п.) и мобильная версия сайта.
- Вывод других полей (`online_users_count` и т. п.).
- Интерпретация и переименование полей.
- Перенос данных между страницами и любое хранилище.

## Decisions

### D1. Источник данных — состояние страницы, а не API
Описано в proposal.md. Альтернатива — API под Android-клиентом. Отклонена: анонимно `403`; токен приложения общий и отзывается при повторном запросе; у `/vacancies/{id}` нет `counters`; порядок выдачи сайта через API не воспроизвести.

### D2. SPA-ответы читаются в background через `webRequest.filterResponseData`
Слушатель `onBeforeRequest` фильтрует `https://hh.ru/search/vacancy*` (пагинация) и `https://hh.ru/shards/vacancy/search*` (смена фильтров; ответ содержит тот же `vacancySearchResult`) с типом `xmlhttprequest` и опцией `blocking`. Каждый чанк сразу передаётся дальше через `filter.write(chunk)`, его копия накапливается. На `onstop` вызывается `filter.close()`, и только после этого копия разбирается. При любой ошибке вызывается `filter.disconnect()`. Ответ страницы никогда не ждёт разбора и не изменяется.
Размер копии ограничен: при превышении лимита (например, 8 МБ) накопление прекращается, а поток продолжает проходить насквозь.

Разобранные значения отправляются только во вкладку-источник через `tabs.sendMessage(details.tabId, …)` и нигде не сохраняются. Если вкладка уже закрыта или ушла со страницы, сообщение просто теряется.

Альтернативы:
- (а) Перехват `XMLHttpRequest`/`fetch` в контексте страницы (`world: "MAIN"`). Это monkeypatching кода сайта, его легче заметить и сломать.
- (б) Повторный запрос из расширения. Нарушает требование «ноль своих запросов» и упирается в антибот.

### D3. Начальное состояние разбирает content script
Content script запускается на `document_idle` для `https://hh.ru/search/vacancy*` и `https://hh.ru/vacancy/*`. Он читает `template.content.textContent` (у `<template>` текст лежит во фрагменте `content`, а собственный `textContent` пуст; браузер сам снимает HTML-экранирование) и делает `JSON.parse`. Отдельный запрос за HTML не нужен.

### D4. Модель данных без переименования

```
 page template --(content script)--+
                                   +--> Map<vacancyId, Fields> --> render
 SPA XHR --(background filter)-----+
            tabs.sendMessage(tabId)
```

- `Fields` — объект с исходными ключами. Для поиска это `{ responsesCount?, totalResponsesCount? }`, для вакансии — `{ vacancyResponsesCount?, totalResponsesCount? }`.
- Порядок вывода фиксирован списком имён полей для каждого типа страницы. Значение принимается, только если это конечное неотрицательное целое; иначе поле считается отсутствующим.
- Словарь живёт в памяти content script и пропадает вместе со страницей.
- `MutationObserver` на `document.body` дорисовывает новые карточки, обработка батчится через `requestAnimationFrame`.
- Гонки «данные раньше карточки» и «карточка раньше данных» решаются тем, что карточка ищет данные при появлении, а при получении сообщения перерисовываются все карточки.

### D5. Отображение
Небольшой блочный элемент выводит поля в формате `<имя поля>: <значение>`, пары разделены `·`. Например: `responsesCount: 40 · totalResponsesCount: 65`.
- Расположение не привязано к строке «Сейчас смотрят N человек», которой может не быть:
  - на поиске бейдж ставится первым ребёнком шапки карточки — ближайшего `div`-предка ссылки `a[data-qa="serp-item__title"]` (между ними только `span`). Строка «Сейчас смотрят» стоит в той же шапке над заголовком, поэтому бейдж оказывается над ней;
  - на вакансии бейдж ставится сразу после последнего элемента с `data-qa` в столбце свойств (родитель `[data-qa="work-experience-text"]`). Строка «Сейчас эту вакансию смотрят» — следующий пункт без `data-qa`, поэтому бейдж оказывается над ней. Если столбец не найден, бейдж ставится сразу под заголовком `h1[data-qa="vacancy-title"]`.
- Оформление повторяет лейбл карточки «Опыт 3-6 лет» (вычисленные стили с живой страницы): фон `rgb(241, 244, 249)`, скругление 8px, отступы 4px 8px, высота 28px, `"hh sans"` 14px/20px.
- Стили изолированы в Shadow DOM, чтобы CSS сайта на них не влиял и они не влияли на сайт.
- Отсутствующие поля пропускаются. Если полей нет совсем, элемент не создаётся.
- Повторная вставка не создаёт дубликатов: элемент помечается атрибутом и обновляется на месте.

### D6. Сборка и тесты
- esbuild бандлит по одному файлу на точку входа (`background`, `content`) в `dist/`. `manifest.json` копируется туда же. Отдельный dev-сервер не нужен, поэтому Vite не используется.
- `tsc --noEmit` проверяет типы, `@types/firefox-webext-browser` даёт типы для `browser.*`.
- Тесты — `node --test` (Node 25 исполняет `.ts` без сборки) на фикстурах JSON, урезанных из реальных ответов.
- `web-ext` используется для `run` и `lint`.
- Зависимости, только dev: `esbuild`, `typescript`, `@types/firefox-webext-browser`, `web-ext`.

## Risks / Trade-offs

- [Внутренние поля hh переименуют или удалят] → Разбор возвращает «нет данных», и интерфейс молчит. Ошибки пишутся в консоль расширения для диагностики.
- [Ошибка в StreamFilter подвесит XHR сайта] → Чанки передаются до любой обработки, на `onstop` сначала вызывается `close()`, все обработчики обёрнуты в `try/catch` с `disconnect()`. Есть ручная проверка на SPA-пагинации.
- [Если SPA-ответ поиска приходит с ещё не известного URL, он пропускается] → Пагинация (`/search/vacancy*`) и смена фильтров (`/shards/vacancy/search*`) проверены вручную. Новые шаблоны URL добавляются по факту наблюдения.
- [Полей у залогиненного пользователя может не быть] → Наблюдения были анонимными. Проверка в залогиненном профиле — отдельная задача в tasks.md.
- [Исходные имена полей непонятны без пояснения] → Это осознанный выбор, пока смысл не подтверждён. Наблюдения о значениях полей описаны в README.
- [Разрешение `webRequestBlocking` выглядит тяжёлым для локального расширения] → Оно приемлемо, потому что публикации в AMO нет, а хост ограничен `hh.ru`.

## Migration Plan

Не требуется: это первая версия. Установка — `about:debugging` → «Загрузить временное дополнение» → `dist/manifest.json` или `web-ext run`. Откат — удалить дополнение.
